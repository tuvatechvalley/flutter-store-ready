# Store review

Goal: before the user uploads a build, tell them — with evidence from their project — what Google Play or Apple App Review will reject, what is risky, and what they still have to fill in the consoles. Talk to the user in their language; the report itself is written in English.

**Read-only.** Do not change, add or delete anything in the project: no fixes, no installs, no builds, no formatting. The only thing you write is the report (see "Where the report goes").

This skill uses the scripts and guides of the **flutter-store-ready** skill from the same repository, installed next to this one. Below, `<kit>` means that folder: `<this skill's folder>/../flutter-store-ready`. If it is missing, tell the user to install the whole repository (all four skills), and stop.

Follow-ups belong to the sibling skills: store forms (Data safety, App Privacy) → **store-forms**; a rejection that already happened → **store-rejection**; fixing what this review found in a Flutter app → **flutter-store-ready**.

## Where the report goes

Use `<project>/build/reports/store-review/` only when git ignores it (`git check-ignore -q build/reports` succeeds — true for standard Flutter and Android projects, often not for React Native / Expo). Otherwise, or when the project is not a git repository, write to a folder outside the project (for example a `store-review-<app>` folder next to it) and say where. If the user names a place, use it.

## 1. Identify the project

| Project type | How to recognize it | Android settings | iOS settings |
|---|---|---|---|
| Flutter | `pubspec.yaml` with `sdk: flutter` | `android/app/build.gradle(.kts)`, `android/app/src/main/AndroidManifest.xml` | `ios/Runner/Info.plist`, `ios/Runner.xcodeproj` |
| React Native (bare) | `package.json` with `react-native`; `android/` and `ios/` committed | same paths as Flutter | `ios/<App>/Info.plist`, `ios/<App>.xcodeproj` |
| Expo (managed / prebuild) | `package.json` with `expo`; `app.json` or `app.config.*` | `app.json` → `expo.android` (+ config plugins) | `app.json` → `expo.ios` (+ config plugins) |
| Native Android | `settings.gradle(.kts)` and `app/build.gradle(.kts)`, no pubspec / package.json | `app/` | — |
| Native iOS | `*.xcodeproj` / `*.xcworkspace`, no pubspec / package.json | — | `<App>/Info.plist`, `<App>.xcodeproj` |

**Expo:** `app.json` / `app.config.*` and the config plugins are the source of truth. An `android/` or `ios/` folder that git ignores was generated by `expo prebuild`; edits made there by hand are lost on the next `prebuild --clean` or EAS build — report any setting that exists only there (signing, `abiFilters`, Proguard / R8) as a risk. Key map:

| Check | Expo key |
|---|---|
| Android id / version | `android.package`, `version`, `android.versionCode` |
| iOS id / build | `ios.bundleIdentifier`, `ios.buildNumber` |
| Permissions | `android.permissions`, `android.blockedPermissions`, `ios.infoPlist` (`NS…UsageDescription`) |
| Export compliance | `ios.config.usesNonExemptEncryption` |
| Privacy manifest | `ios.privacyManifests` |
| Target SDK, cleartext, other Gradle settings | `expo-build-properties` plugin; `eas.json` for build profiles and signing |
| iPad | `ios.supportsTablet` |

Ask which store(s) to cover only when the user's words do not say and the project is set up for both (an Android id and an iOS bundle id both exist).

## 2. Run the checks

### Flutter — automated

```sh
dart run <kit>/scripts/project_report.dart <project> --out <report folder> [--skip-gates] [--skip-play | --skip-ios] [--last-version-code N] [--last-build-number N]
```

Without `--skip-gates` it runs `dart format` (check only), `flutter analyze` and `flutter test` in the project; these only touch git-ignored build files, but they take minutes on a large app — pass `--skip-gates` when the user asks only about store rules, or when `flutter` is not installed, and say the gates were not run. Exit code 1 only means "blocking items found".

Keep the script's output files as they are; your reviewed report is a separate file (next section).

### Other project types — checklist review

The scripts understand only Flutter projects today. Review by reading the files in the table above, with these guides:

- `<kit>/GOOGLE-PLAY-RELEASE.md` — signing, ids, target SDK, manifest, cleartext, permissions, Play Console tasks;
- `<kit>/APP-STORE-RELEASE.md` — section 4 (project settings) and section 6 (App Store Connect);
- `<kit>/STORE-POLICIES.md` — purchases, ads and consent, user content, AI, data declarations, accounts, reviewers, release fingerprints, apps children use;
- `<kit>/ERROR-HANDLING.md` sections 3–5 — error messages users understand, the four screen states, timeouts and retries (the same in every framework).

Dependencies are in `package.json` (React Native / Expo), Gradle files (Android) or Podfile / Swift packages (iOS) instead of `pubspec.yaml`. Anything that can only be verified on a build (the merged manifest, the final target SDK when dependencies are not installed, 16 KB alignment, the signed bundle) is a 📝 "verify on the build" item, not ❌ — say what to check and where (Play Console → App bundle explorer; the EAS build log).

## 3. Read the code (both paths)

Scripts match text patterns; they miss things and flag correct code. In this order, and stop when the answer is clear:

1. **Every ❌ finding** — open the file; confirm, correct the severity, or drop it with a one-line reason.
2. **Accounts** — sign-in, in-app deletion that really deletes on the server, reviewer access.
3. **Money** — purchases (restore, paywall terms, store billing for digital goods).
4. **Data leaving the device** — every network call and SDK; compare with the privacy policy text.
5. **Permissions** — where each prompt is triggered, and for whom.
6. **The rest** of `<kit>/AUDIT-AND-REPORTING.md`, "Then read the code", as time allows; say what you did not cover.

## 4. Report

Write `PROJECT_REPORT.md` in the report folder (for Flutter, next to the script's files; rename nothing). Use the format of `<kit>/AUDIT-AND-REPORTING.md`, "Report rules", and its severity definition: ❌ **blocking** = breaks the app for users, exposes their data, or gets the build rejected; ⚠️ risky or recommended; 📝 the user's tasks in Play Console / App Store Connect or "verify on the build"; ✅ checked and fine.

1. Verdict first: ❌ NOT READY / ⚠️ ALMOST READY / ✅ READY, per store when they differ.
2. Each finding: what, where (`file:line`), why it matters (name the guideline or policy when it is a store rule), how to fix it.
3. A section **"Changes to the automated findings"** (Flutter): each finding you dropped or re-graded, with the reason; findings the scripts missed.
4. For a checklist review, state at the top: "Checklist review — no automated checks were run for this project type."
5. No passwords, keys, tokens or people's names from certificates in the report.

In chat, in the user's language, 3–6 lines: the verdict, the blocking items, the single next step, and the report path. Do not paste the report.

## Never

- Change code, settings, dependencies or the consoles. If the user then asks for fixes, use **flutter-store-ready** (Flutter) or fix them as asked.
- Present a pattern match as a confirmed violation without opening the file.
- Quote a store rule, date or API level from memory when it decides the verdict: the guides link the official pages, and policies change every year. If it cannot be checked, say "verify" instead of guessing.
